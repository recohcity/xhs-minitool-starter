# 真需求诊断

## 目的

根据真实行为证据判断产品当前处于哪一层：有人口头感兴趣、存在待验证的需求、需求存在但方案未证、方案有效但尚未形成重复选择，或一个窄场景已经得到行为验证。

坚持一个底层判断：**需求通过人在现实约束下反复发生的行为显现。** 不用产品功能、创始人投入、问卷好评、候补名单或一次性成交代替需求证据。

始终拆开三个问题：

1. **需求真实性**：具体的人是否在具体时刻反复遇到障碍，并已为解决它付出代价？
2. **方案有效性**：产品是否在真实场景中让结果发生可感知变化，并优于当前替代办法？
3. **重复选择**：新鲜感过去后，用户是否继续使用、迁移、付费、续费、复购或主动推荐？

只证明前一层时，不得宣布后一层成立。

## 诊断原则

- 先看最近一次真实事件，再看抽象人群和市场描述。
- 先问用户当前怎样解决，再讨论准备开发什么。
- 记录动作、次数、时间、金钱、迁移和后果；降低口头态度的权重。
- 把“不做任何事”视为重要反证。确认问题是否弱到可以继续忍受。
- 观察无辅助使用。演示成功只能证明演示者会操作。
- 把现状和拼凑出来的替代方案当作主要竞争对手。
- 区分事实、推断和未知，不虚构访谈、数据、动机或付费意愿。
- 把评分当作定位断点的辅助，不把分数包装成科学测量。

## 工作流

### 1. 判断产品阶段

从已有材料识别阶段，不要求用户选择内部流程：

- **想法期**：没有可供真实用户使用的版本。
- **原型期**：已有可试用版本，尚未形成稳定用户。
- **使用期**：已有真实使用，付费证据不足或没有付费设计。
- **付费期**：已有真实付款，需要检查结果、留存与重复购买。

先提取用户已经给出的事实。材料不足时，每次只追问一个最能改变结论的问题。按阶段使用 [question-flow.md](references/question-flow.md)，避免让用户重复背景。

### 2. 锁定真实场景与用户任务

把产品语言翻译为任务语言：

> 当 `{具体的人}` 处于 `{触发场景}`，他想把 `{卡住的进展}` 推进到 `{可感知结果}`，当前依靠 `{替代办法}`，因此承担 `{现实代价}`。

拒绝把“年轻人”“中小企业”“所有创作者”等类别直接当作用户证据。至少找到一个真实的人、一次近期发生的事件和一个不解决会产生的后果。

### 3. 建立需求证据卡

记录六项：具体的人、发生时刻、想完成的进步、现实障碍、当前绕路与代价、已经发生的验证行为。

需要交付表格时，复制 [demand-evidence-card.md](assets/demand-evidence-card.md)。连续收集多张卡后，检查场景、障碍和付代价行为是否同时跨人、跨时间重复。

### 4. 评定承诺强度

按已发生的最强行为标记证据等级：

- E0：口头喜欢、问卷意愿、点赞、候补名单或注册。
- E1：围绕同一问题重复求助。
- E2：自行拼接工具、表格、人工流程或雇人凑合。
- E3：投入预约、试用、填写资料、学习或排队等时间。
- E4：导入数据、改变流程、邀请同事或放弃旧方案。
- E5：按明确条件支付定金、预购或正常价格。
- E6：新鲜感过去后持续使用、续费、复购或主动推荐。

付款与持续选择分别记录。一次低价尝鲜、人情单或冲动购买不能自动升级为 E6。

### 5. 检查方案是否真的解决

沿着一条完整链检查：

`具体场景 → 想完成的进步 → 产品机制 → 可感知结果 → 行为确认`

逐项判断：

1. 产品依靠什么机制改变结果？
2. 用户能否在没有讲解和代操作时完成关键任务？
3. 使用前后发生了什么可观察变化？
4. 相比现有替代办法，在哪个选择标准上更好？
5. 用户下一次遇到相同场景时是否再次选择？

当前替代办法明显更便宜、更顺手或更可靠时，判定当前场景尚未形成方案匹配，即使产品本身功能优秀。

### 6. 应用否决条件与评分

读取 [diagnostic-rubric.md](references/diagnostic-rubric.md)，先应用否决条件，再看分数。允许手工评分；需要可复算结果时运行：

```bash
python scripts/score_evidence.py path/to/evidence.json
```

根据证据给出且只给出一个当前结论：

- **证据不足**
- **需求过弱／疑似伪需求**
- **真需求候选，方案未证**
- **需求存在，当前方案未解决**
- **方案有效，重复选择未证**
- **强场景初步成立**
- **重复需求已验证**

禁止把“强场景初步成立”直接写成 PMF。市场规模、获客效率和单位经济需要另外验证。

### 7. 设计最小反证实验

针对当前最弱的一环，只设计一个最低成本测试。明确写出：

- 找谁：处在什么具体场景的真实用户；
- 给什么：可在数天内交付的最窄方案，必要时先人工完成；
- 要什么承诺：资料、时间、迁移、定金、正常付款或再次使用；
- 看什么结果：使用前后变化和无辅助完成情况；
- 何时结束：明确时间盒；
- 怎样判输赢：测试前写出通过、失败与改写阈值。

优先设计能够推翻当前信念的实验，不设计只能收获赞美的展示。

## 输出格式

默认输出紧凑报告。证据少时保留“未知”，不补写完整故事。

```markdown
# 真需求诊断报告

## 一句话结论
- 当前判定：{七种结论之一}
- 建设决策：{暂停开发／只测最窄方案／修正方案／继续深挖当前场景}
- 置信度：{低／中／高，并说明依据}

## 用户真正要完成的事
当 {具体的人} 处于 {触发场景}，他想 {推进的进展}，以便 {可感知结果}。

## 证据
| 层次 | 已知事实 | 强度 | 缺口 |
|---|---|---|---|
| 需求真实性 | {…} | {弱／中／强} | {…} |
| 方案有效性 | {…} | {未测／弱／中／强} | {…} |
| 重复选择 | {…} | {未测／弱／中／强} | {…} |

## 断点与反证
- 当前最先断掉的一环：{…}
- 最强反证：{…}
- 哪条新证据会改变结论：{…}

## 下一次最小测试
- 对象：{…}
- 交付：{…}
- 要求的真实承诺：{…}
- 通过标准：{…}
- 失败标准：{…}
- 时间盒：{…}

## 暂不该做
{在验证前不应继续投入的功能、推广或规模化动作}
```

## 边界

- 不把需求诊断扩写成完整商业模式、定价、获客或竞争战略咨询。
- 不把付费当作唯一需求证据；同时单独标注商业付费是否得到验证。
- 不把留存自动解释为获得结果；检查习惯、锁定、补贴和被动默认。
- 不把单个用户的强烈需求外推成大市场。
- 不把企业购买者、使用者、审批者和受益者默认成同一个人。
- 不引用来源受限或标明禁止商用的材料。
- 需要解释方法依据时读取 [method-basis.md](references/method-basis.md)；需要校准判断时读取 [worked-examples.md](references/worked-examples.md)。
